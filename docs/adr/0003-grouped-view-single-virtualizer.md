# Grouped View uses one flattened virtualizer, not one table per Service Group

The original Grouped View implementation mounted a separate `LogRecordsTable` (and separate `useVirtualizer`) per Service Group, each in its own `600px` scrollbox. That defeats the point of virtualization: the page holds N independent scroll containers instead of one bounded view, row `key`s and expanded-row state were keyed by per-table array index (safe only because each group had its own 0-based array), and UX degrades into scroll-in-scroll as the number of services grows. We instead flatten Grouped View into a single row list — group-header rows interleaved with log-record rows — fed into one `useVirtualizer`, with rows keyed by stable log identity rather than position. Groups default to collapsed so the initial flattened list stays small regardless of dataset size; expanding a group inserts its rows into the same list rather than opening a nested scroll region. Flat View and Grouped View therefore share the same virtualization engine and row-rendering component, differing only in whether header rows are present and which rows are filtered out by collapse state.
